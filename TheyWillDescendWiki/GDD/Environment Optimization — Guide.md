## 1. Измерять причину и время кадра

Unity рекомендует проверять сборку на целевом устройстве, разделять CPU/GPU и сначала находить ограничивающую часть кадра. Результаты Editor полезны для сравнений, но включают редакторские расходы. [Unity: profiling workflow](https://unity.com/how-to/best-practices-for-profiling-game-performance).

Наш протокол: одинаковая камера, разрешение, время суток и набор объектов; прогрев; повтор A → B → A; медиана и высокие процентили времени кадра; отдельно CPU main/render, GPU, ожидания, draw calls и память. Погоду/симуляцию либо воспроизводить, либо явно описывать различия. Не суммировать CPU и GPU как последовательные независимые затраты.

`Gfx.WaitForPresentOnGfxThread` может отражать ожидание GPU/представления кадра; `WaitForTargetFPS` — ограничение частоты. Надпись CPU сама по себе не доказывает активную работу процессора. Разбирать Timeline соседних потоков. [Unity: Profiler markers](https://docs.unity3d.com/6000.0/Documentation/Manual/profiler-markers.html).

AMD также подчёркивает необходимость отделять CPU-bound от GPU-bound и учитывать накладные расходы development-сборок. Его Radeon-инструменты рассчитаны на AMD; наш текущий GTX 1080 Ti не превращается в подходящее устройство для RGP. [AMD: Unity CPU profiling guide](https://gpuopen.com/learn/unity-cpu-profiling-guide/).

Пользователь пока не выбрал целевой FPS. Не назначать бюджет окружения молча. Справочно: 60 FPS = 16.67 мс на весь кадр, 120 FPS = 8.33 мс; игре ещё понадобятся город, жители, интерфейс и погода.

## 2. Плато: стоимость материала отдельно от геометрии

Стандартный Triplanar делает выборки текстуры по трём проекциям и смешивает их; это видно в генерируемом коде узла. Дополнительные карты/слои умножают эту работу. Но нельзя считать все узлы файла активными или заявлять точное число texture fetch без компиляции shader variant. [Unity: Triplanar node](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Triplanar-Node.html).

**Эксперимент для нас:** текущая модель/материал → та же модель с простым Lit → исходный материал без casting shadows → Renderer выключен. Это разные факторы, проверять раздельно. Затем отключать конкретные слои через реальный упрощённый вариант, а не менять сразу всё.

Идеи, если подтвердится дорогой fragment shader: для ровного верха проверить одну XZ-проекцию; трипланар оставить склонам; часть масок/процедурной детализации запечь в текстуру; сохранить surface mask и рисунок перехода. Это проектные гипотезы, не приказ разрезать модель. Дополнительный материал/Renderer тоже имеет цену; визуальный стык недопустим.

**Важная ловушка Shader Graph:** обычный Branch не гарантирует пропуск невыбранной тяжёлой ветви — документация описывает вычисление обеих сторон. Нулевой вес overlay в Lerp тоже не следует считать отключением его texture samples. Для гарантированно упрощённой версии рассмотреть compile-time keyword/отдельный shader и проверить результат; не плодить десятки комбинаций keywords. [Unity: Branch node](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Branch-Node.html).

## 3. Плотный лес: контролировать площадь и перекрытия листвы

Плоскости с группами листьев и отдельные уровни общего/мелкого движения — проверенный подход. В GPU Gems 3 описаны общий изгиб дерева, мелкая деформация и параметры в vertex colors; это полезная основа для авторинга, а не современный численный бюджет для нашего ПК. [NVIDIA: vegetation in Crysis](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-16-vegetation-procedural-animation-and-shading-crysis).

Наши решения для следующих деревьев:

- Сначала крупный силуэт с RTS-камеры, затем карточки; не набивать внутренность невидимыми слоями.
- Обрезать карточку разумно близко к силуэту веточки: несколько дополнительных вершин могут быть выгоднее большой пустой области с альфой. Слишком мелкая нарезка тоже не бесплатна.
- Для LOD сохранять объём кроны, уменьшая перекрытия, мелкие ветки и сложность материала/ветра, а не только счётчик треугольников.
- Дальний фон может быть группами упрощённых крон или многоракурсными impostors. Одна вертикальная картинка не годится автоматически для нашей камеры сверху и полного yaw.
- Продолжать проверять shadow proxy как отдельную стоимость. Наша схема улучшила вид тени, но не является универсальной гарантией ускорения любого дерева.

Большая площадь прозрачных/вырезаемых поверхностей и повторная обработка пикселей — отдельная GPU-проблема. Низкое число треугольников не доказывает дешевизну кроны. Unity отдельно рассматривает стоимость shader, света и теней. [Unity: PC/console graphics optimization](https://unity.com/how-to/performance-optimization-high-end-graphics).

У wind-меша bounds должны вмещать максимальное колыхание, но чрезмерное расширение ухудшает отсечение. Для наших LOD сохранять UV1/UV2, COLOR, hinges, высоту и tangent basis. Это контракт `NaturalTreeWind.hlsl`, а не необязательные каналы для удаления ради размера файла.

## 4. Пакетная отрисовка: уменьшать CPU-работу осмысленно

SRP Batcher уменьшает переключения render state между draw calls, а не объединяет весь лес в один draw. Разные материалы с одним вариантом shader могут быть совместимы с SRP batching; одинаковое имя материала ещё не подтверждает instancing. [Unity: SRP Batcher](https://docs.unity3d.com/6000.4/Documentation/Manual/SRPBatcher.html).

GPU Resident Drawer — подходящий **кандидат** для наших повторяющихся деревьев/камней: он использует BatchRendererGroup и GPU instancing, разгружая CPU. В 6000.4 нужны подходящий renderer/API и совместимые объекты. [Unity: enable GPU Resident Drawer](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/gpu-resident-drawer.html).

До пробы проверить DOTS-instancing shader support, custom wind и все проходы, отсутствие MaterialPropertyBlock/per-instance render callbacks и другие ограничения. MPB не является универсально правильным способом раскраски нашего будущего леса: он несовместим с описанным GRD-путём. [Unity: object compatibility](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/make-object-compatible-gpu-rendering.html).

Выигрыш GRD зависит от сцены; сравнить в Play/build, не по одной Scene View. Static batching не смешивать с новым путём вслепую: Unity предлагает отключать его при оценке GRD. [Unity: GRD performance considerations](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/gpu-resident-drawer-performance.html).

Правила авторинга: общий mesh asset, общие материалы/атласы, ограниченное число variants. Не создавать `renderer.material` для каждого дерева и не объединять весь лес одним огромным мешем: такие крайности мешают повторному использованию, отдельной вырубке и отсечению. Фактический путь проверять Frame Debugger, пользу — CPU render-thread time. Дорогой shader от instancing дешевле не становится.

## 5. Свет и тени: сначала лава и крупные источники

Point light с тенями требует shadow map для шести направлений; стоимость может быть сопоставима с шестью spot shadows. Сравнить у лавы свет без теней, отдельные необходимые shadow lights и текущий вариант. Замена Point на Spot допустима только при подходящей форме освещения. [Unity: shadow mapping](https://docs.unity.com/en-us/engine/6000.0/manual/lighting-overview/shadows/shadow-realtime/shadow-mapping).

Для нашей камеры проверить отдельно shadow distance 200 м против меньших значений, 4 каскада против 2, качество soft shadows. Сравнивать крупный план, край платформы, лес и движение солнца. Пользователь уже отверг заметное включение/выключение теней травы по зуму — не возвращать его без новой задачи.

**Forward+ уже включён:** Additional Lights Per Object Limit = 4 не является рабочим ограничителем числа источников в этом rendering path. Unity прямо исключает Forward+ из действия этой настройки. Имеют значение реальные источники, их радиусы, экранное покрытие и тени. [Unity: URP optimization settings](https://docs.unity3d.com/6000.4/Documentation/Manual/urp/optimize-for-better-performance.html).

Измерять лаву, её источники и частицы отдельными переключениями. Не выдавать результат отключения целой группы за цену одного компонента и не называть лаву главным тормозом до проверки.

## 6. Запекание с учётом дня/ночи и удаления деревьев

Baked lighting хранит заранее рассчитанный результат; изменение Mixed light обновляет realtime-часть, но не уже запечённую составляющую. Поэтому запечь весь свет и затем свободно менять его нельзя. [Unity: light modes](https://docs.unity3d.com/6000.0/Documentation/Manual/LightMode-Baked.html).

Наше направление: рассмотреть постоянный свет лавы на неподвижной скале отдельно от движущегося солнца, будущего города, персонажей и ветровой кроны. Для динамики отдельно выбрать подходящие probes/realtime-источники; APV не внедрять только ради обещания ускорения.

**Уточнение пользователя 2026-11-05:** анимация рубки/падения не обязательна. Дерево может просто удаляться или сменять состояние. Даже без анимации его навсегда запечённая тень на земле останется после удаления. Удаляемые деревья не должны оставлять постоянный отпечаток такого рода; игровые состояния и визуальное удаление проектируются отдельно.

UV1/UV2 наших деревьев заняты ветром. Не запускать генерацию lightmap UV поверх этих каналов и не удалять их при оптимизации. Нужен явный новый контракт, если когда-нибудь потребуется другое использование.

## 7. Сглаживание, экранные проходы и частицы

MSAA уже помог пользователю убрать мерцание узоров пирамиды: не отключать его ради сухой цифры. Проверить **8× → 4× → 2×** по качеству/времени GPU. AMD RDNA guide тоже рассматривает ограничение MSAA как возможность экономии, но аппаратные советы RDNA нельзя переносить на Pascal как гарантированный результат. [AMD: RDNA performance guide](https://gpuopen.com/learn/rdna-performance-guide/).

Приоритет для наших VFX: количество крупных перекрывающихся дымовых/лавовых плоскостей, площадь на экране, материал, soft particles, а затем число частиц. Проверить верхний вид с дымом и будущий ливень; несколько больших слоёв способны быть дороже многих маленьких искр. Это гипотезы для контролируемого A/B, не результаты текущего исследования.

Depth Texture, Opaque Texture, SSAO, bloom и другие проходы отключать по одному только после проверки использования. Lava/soft particles могут зависеть от camera textures. Список доступных настроек не означает, что всё перечисленное сейчас активно или лишнее.

## 8. Текстуры и импорт: память тоже входит в бюджет

Проверять разрешение по реальному экранному размеру, mipmaps, платформенное сжатие и необходимость Read/Write. Для alpha-tested листвы проверить Preserve Coverage и соответствующий alpha cutoff: это помогает сохранять покрытие в mipmaps; это не уменьшение количества карточек. Read/Write текстур хранит CPU-копию, поэтому включать только по необходимости. [Unity: texture import settings](https://docs.unity3d.com/6000.0/Documentation/Manual/texture-type-default.html).

Для нас: не назначать 4K/8K каждому маленькому кусту; не терять альфу при сжатии; data maps импортировать с корректным color space. Streaming внедрять только с проверкой world-space/triplanar масштаба и реальных mip-уровней. Не включать его массово, ожидая автоматического роста FPS.

## 9. Видимость, дальний фон и цена логики

Обычный frustum culling не равен отсечению объектов за другими объектами. Встроенный baked occlusion culling требует данных/CPU и особенно полезен для разделённых закрытых пространств; открытое плато не гарантирует такой выигрыш. Динамические объекты могут отсекаться, но не становятся baked occluders. [Unity: occlusion culling](https://docs.unity.com/en-us/engine/6000.5/manual/cameras/occlusion-culling/occlusion-culling).

Для нас сначала достаточно надёжных bounds, LOD и разделения фона на разумные группы. GPU occlusion — отдельный эксперимент после проверки GRD. Вырубаемый лес не делать неизменным baked-препятствием, от которого зависит видимость мира за ним.

Внешнему лесу не нужны собственный Update, Collider, Rigidbody или ECS-состояние ресурсов без игровой задачи. Общий ветер обновляет параметры централизованно; деформацию делает GPU. При дальнейшем росте города измерять ECS jobs, синхронизации, GC, UI и VFX отдельно. Перенос декоративного леса в ECS не уменьшает автоматически fragment shading, overdraw и стоимость теней.

## Очередь следующих проверок

| Порядок | Проверка | Критерий решения |
| --- | --- | --- |
| 1 | Плато: простой материал / тени / Renderer, фиксированная камера | Разделены shader GPU, geometry/passes и CPU/wait; изменение только по результату |
| 2 | Лава / её свет / её частицы по отдельности | Видно, какой компонент даёт наибольшую прибавку; есть сопоставимые A/B |
| 3 | MSAA 8/4/2 и отдельно тени 200 м/4 каскада против меньших настроек | Есть экономия без возврата ряби и заметного исчезновения теней |
| 4 | GRD для существующего леса/камней с проверкой compatibility | Снизилось реальное CPU render time, корректны ветер/LOD/тени, GPU не ухудшился существенно |
| 5 | Листва: плотные карточки, уменьшение перекрытий, дешёвый фон | Сохранён объём с RTS-камеры; сравнение GPU при одной композиции |
| 6 | Представительная PC-сборка в целевом разрешении | Повторены низкая/высокая камера, пан к джунглям, день/ночь; затем тест с городом/жителями и погодой |

Это очередь исследования, не обязательство применить каждый приём. После каждого изменения сохранять кадр и время кадра, а не только новый FPS. Если узкое место изменилось, пересматривать порядок.

## Перед принятием нового ассета

- Силуэт читается сверху и снизу; масштаб/pivot согласованы с миром.
- Известны треугольники, material slots, texture sizes, LOD и shadow geometry.
- Повторяющиеся экземпляры используют общие mesh/material assets.
- Сохранены авторские UV/COLOR ветра и surface mask; bounds достаточно точны.
- Для удаляемого объекта определено, что происходит с его тенью и probes после исчезновения.
- Проверен сектор в контексте сцены, не только один объект в пустом окне.
- Есть измерение на нужной плотности; нельзя экстраполировать один дешёвый экземпляр на весь лес.

**Правило дальнейшей работы:** выбирать детализацию по вкладу в итоговый кадр. Невидимые внутренние слои, сложный дальний ветер и многочисленные тени не добавляют сцене качества пропорционально их стоимости.
