## 3. Зафиксированные решения (Ф0) — не переоткрывать

### 3.1. Пауза здания — РЕШЕНО

Штат **остаётся**. Пауза останавливает только рецепт: люди ходят на работу, ничего не производят.

Сейчас `WorkforceDispatchSystem` при `Paused` считает `desired = 0` и отпускает людей. Это баг относительно решения. Чинится в **Ф3**. Комментарий на `Workplace.Paused` и текст инспектора уже говорят правду.

Две ортогональные оси:

- `DesiredWorkers` — сколько людей хочу.
- `Paused` — работает ли рецепт.

Отпустить людей = штат в 0, не пауза.

### 3.2. Кто пишет желание — РЕШЕНО для реализации

`DesiredWorkers` пишет **только** игрок (кнопки инспектора) и восстановление сейва. Системы **никогда** его не переписывают.

Сейчас диспетчер при нехватке людей делает `DesiredWorkers = current + assigned`. Если рабочий умрёт или людей временно нет, желание схлопывается навсегда. Это и есть причина, по которой паттерн desired state заводили — и сейчас он сломан.

Эффективная цель: `target = min(DesiredWorkers, slots)`. `Paused` на штат не влияет. Недобор — нормальное состояние.

`BuildingDismantle.Begin` сегодня пишет `DesiredWorkers = 0` — это **не** игрок. В Ф3 снос перестаёт трогать желание как «удобство»: дом всё равно уничтожится; отпускать людей должен диспетчер по исчезнувшему `Workplace` (после Ф2 — по висячей `Entity`).

### 3.3. Порядок раздачи при нехватке — РЕШЕНО для среза

Стабильный порядок по `Building.Id` (ключ сохранения). Не порядок чанков. Поле приоритета игрока — позже, не сейчас.

### 3.4. Слайдеры пирамиды — ОТЛОЖЕНО

Не трогать `SetPyramidFeedRequest` / `ConsumeSetPyramidFeedCommandsSystem` / запись `PyramidFeedLine` из UI через запрос. Когда будет новый дизайн — отдельная задача.

### 3.5. Какой вход для чего — таблица канона

| Природа | Канал | Примеры сейчас / после |
| --- | --- | --- |
| Постоянная настройка уже существующей сущности | Поле на этой `Entity` | `Workplace.DesiredWorkers`, `Workplace.Paused`. (Слайдер пирамиды — позже) |
| Разовое действие над миром | Request-сущность (`IComponentData` на одноразовой entity) | поставить, снести, заспавнить, выбрать исследование |
| Упорядоченный поток команд одного вида за кадр | Буфер на сессии | `SimClockCommand` (пауза, потом скорость — строго по порядку) |
| Наружу из симуляции | Буфер-событие на сессии | `BuildingRejectedEvent` |

Почему часы — буфер, а не request: порядок обхода request-сущностей в запросе не гарантирован. Несколько clock-команд за кадр должны примениться в порядке постановки.

## 4. Порядок фаз и почему нельзя переставить

```text
Ф1  Чистый мир рана     wipe + create, без фаз и despawn-команд
Ф2  Идентичность Entity int Id → Entity в геймплейных ссылках
Ф3  Честный desired     диспетчер не пишет желание; пауза не отпускает
Ф4  Входы игрока        папки, имена, один гейт «ран идёт»
Ф5  Чтение Presentation панели без CreateEntityQuery на кадр
```

- **Ф1 раньше Ф2.** Сейв сейчас восстанавливает дома через `PlaceBuildingRequest` с `BuildingId`, рабочих — через `SpawnAgentRequest` с `WorkplaceBuildingId`. Если сначала сменить поля на `Entity`, придётся тащить маппинг id→Entity через очередь запросов на несколько кадров. Если сначала прямое восстановление в одном методе — маппинг это локальная `NativeHashMap<int, Entity>` внутри `SnapshotRestore.Apply`.
- **Ф2 раньше Ф3 и Ф5.** Почти все линейные поиски — следствие `int Id`. Чинить их до смены идентичности = сделать работу дважды.
- **Ф4 после Ф1.** Половина буферов (`PendingScenarioPlace`, `DespawnAll*`, `PendingScenarioSpawns`) умрёт в Ф1. Унифицировать оставшееся проще.
- **Ф5 после Ф2.** Панели должны держать `Entity`, а не искать дом по id каждый кадр.

## 5. Железные запреты

1. **`EntityManager.DestroyEntity(em.UniversalQuery)` нельзя.** В default world живут служебные сущности пакетов (Entities Graphics, время мира). Их смерть ломает мир. Только тег `RunScoped` (Ф1).
2. **Симуляция не ссылается на Content-префабы и не вызывает UI/FMOD.** Bootstrap пока живёт в Presentation (`SimulationBootstrap`), потому что читает `BuildingCatalogAsset`. Не переносить bootstrap в Simulation в этих фазах — это CMS из документа 05.
3. **UI не пишет исходы.** Можно писать желание (`DesiredWorkers`, `Paused`) и постить request/буфер. Нельзя писать `AssignedCount`, `WorkingCount`, стоки, лояльность, позу агента.
4. **Не вводить `IEconomyService` / VContainer в `ISystem`.**
5. **Не чинить «заодно»** известные баги вне фазы (дороги не в сейве, `bus:/Ambience`, кухня сценария на клетке c=100 r=7), если фаза их не касается. Исключение: если файл и так переписывается и правка — две строки без нового поведения — можно, и написать в отчёте фазы.
6. **Не коммитить без просьбы пользователя.**

## 6. Как работать внутри фазы

1. Прочитать файл фазы в этой папке целиком.
2. Свериться с `01 Inventory` (что где лежит **сейчас**).
3. Идти по «Порядок работ» в файле фазы, не параллелить несвязанные рефакторинги.
4. После каждого крупного шага — компиляция (консоль Unity без ошибок вашей сборки).
5. Чек-лист Play из файла фазы + общий чек-лист ниже.
6. Обновить вики, перечисленные в конце файла фазы.
7. Остановиться и отдать пользователю: что сделано, что проверить руками, что осталось.

Общий Play после **каждой** фазы:

1. Компиляция, консоль чистая на входе в Play (известные FMOD-warnings шины `bus:/Ambience` и отказ кухни Normal-сценария `c=100 r=7` — не ваши, не маскировать).
2. Меню → новая игра → поставить дом → назначить людей → дождаться производства.
3. Снести дом с людьми и дом со стройкой.
4. Пауза здания, x1/x2/x3, Esc.
5. Сохранить → меню → загрузить: дома, стройки, штат, лояльность, эра, истории. (Слайдеры пирамиды и дороги — как сейчас; дороги в сейве нет, не регрессировать остальное.)
6. Меню → новая игра без перезапуска Play.
7. Debug-запуск с предрасставленными домами (`EditorRunLaunch.Debug` или рестарт Debug).

Прогонять и на `Game.unity`, и хотя бы раз на `Blockout/GameBlockout.unity` (тот же `#GameRun`).
